# 개발 기록

왜 이렇게 만들었는지, 무엇을 시도했다 접었는지, 지금 어디까지 왔는지.
다른 기기에서 이어서 작업할 때 맥락 없이 시작하지 않도록 남긴다.

기술적 함정은 [`CLAUDE.md`](../CLAUDE.md) 에, 라이선스 근거는
[`THIRD_PARTY.md`](THIRD_PARTY.md) 에 따로 있다.

## 시작점

실제 운영 중인 팰월드 서버(Contabo VPS, 도쿄 리전, Docker)의 세이브를
Python으로 편집하던 중 두 가지가 걸렸다.

**배포.** 세이브 하나를 열려고 서버에 venv를 만들고 C 확장을 빌드해야 했다.

**안정성.** 46MB GVAS를 파싱한 뒤 Python 3.12가 객체 그래프를 해제하다가
**재현성 있게 세그폴트**를 냈다. 매번 같은 명령 주소, OOM 아님. 파싱 자체는
끝난 뒤라 결과는 맞는데 종료할 때 죽었고, 파이프로 넘기면 stdout 버퍼가
비워지지 않아 출력이 통째로 사라졌다. `os._exit(0)` 로 정리 단계를 건너뛰어
우회했다.

Go에는 그 문제가 구조적으로 없다. 단일 실행 파일이 되는 것도 크다.

## 언어 선택

처음엔 C# 또는 Rust를 권했다. GVAS는 동적 태그드 트리라 Rust의 enum이 가장
잘 맞고, 윈도우 GUI는 C#이 투입 대비 산출이 좋다.

그 판단을 뒤집은 건 **기존 프로젝트의 존재**였다. `NanachiDeprotector2`가
이미 Go + Wails로 출시돼 있었고, 거기서 StormLib DLL을 **CGO 없이**
`windows.NewLazyDLL` + syscall로 붙여 쓰고 있었다. MPQ·BLP 같은 바이너리
포맷 파싱 경험도 있었다.

즉 내가 걱정한 난점(네이티브 바인딩, GUI, 바이너리 파싱)이 이미 다 풀려
있었다. 언어의 이론적 적합도보다 **작성자의 기존 레버리지가 크다**.

남은 진짜 마찰은 GVAS를 Go로 표현하는 것뿐이었고, 그건 `map[string]any` 대신
타입드 프로퍼티로 해결했다.

## Oodle — 예상보다 오래 걸린 구간

`.sav` 는 Oodle(Kraken) 압축이다. Oodle은 Epic 소유 독점 코덱.

**시도 1: 게임에서 DLL 빌려오기 → 불가능.** UE5는 Oodle을 실행 파일에 정적
링크한다. Palworld 설치 폴더에 `oo2core*.dll` 이 아예 없다. 확인 완료.

**시도 2: 상류 ooz → 반쪽.** `powzix/ooz` 는 **디컴프레션 전용**이다. 세이브를
쓰려면 인코더가 필요한데 없다. 이걸 모르고 클론했다가 한 번 막혔다.

**해결: `zao/ooz`.** 인코더(`compress.cpp`, `compr_*.cpp`)가 추가된 포크.
파일 목록이 palooz가 벤더링한 것과 정확히 일치한다.

MinGW로 빌드할 때 우회 두 개가 필요했다. ooz가 MSVC/리눅스 gcc 기준이라
`static _rotl` 이 MinGW의 `extern` 선언과 충돌한다 → `-fpermissive`, 그러면
번역 단위마다 정의가 생기므로 → `-Wl,--allow-multiple-definition`.
둘 다 `third_party/oodle/build.sh` 에 이유와 함께 주석으로 남겼다.

**GPL은 여기서 결정됐다.** ooz가 GPL-3이므로 프로젝트 전체가 GPL-3.
별도 exe로 분리해 회피하는 방법도 있었지만(기존 프로젝트가 `pjass.exe` 로
하던 방식), 46MB를 파이핑하는 복잡도를 감수할 이유가 없었다.

## GVAS — 진짜 산

전체 46MB 트리를 디코드하고 **바이트 단위로 동일하게** 다시 인코드하는 게
목표였다. 두 가지가 발목을 잡았다.

**`size` 필드의 의미.** 페이로드 전체가 아니라 **타입별 헤더(optional GUID
포함) 이후**만 센다. `IntProperty` 는 5바이트를 쓰면서 4를 기록하고,
`BoolProperty` 는 2바이트를 쓰면서 0을 기록한다. 이걸 모르면 파일 전체가
어긋난다 — 실제로 바이트 1817(첫 프로퍼티 `Version` 의 size 필드)에서 걸렸다.

**커스텀 코덱은 필요 없었다.** palsav는 17개 경로에 전용 핸들러를 등록한다.
그대로 따라 했다가 오히려 버그가 났다 — `size` 만큼 통째로 삼키면 배열 헤더
17바이트를 건너뛰어 스트림이 어긋난다. 특수 처리를 **빼니까** 통과했다.
그 페이로드들은 전부 일반 디코더가 이미 파싱하는 ByteProperty 배열이었다.

경로 목록은 `PalworldRawDataPaths` 로 남겼다. 디코딩용이 아니라 어느 blob이
해석할 값어치가 있는지 표시하는 용도다.

## 타입 안전성 — 이걸 위해 Go를 골랐다

Python으로 작업하다 실제로 깨진 지점:

```python
sp["Level"]["value"] = 80          # 틀림. dict를 int로 덮어씀
sp["Level"]["value"]["value"] = 80 # 맞음. ByteProperty는 한 겹 더 중첩
```

`Exp` 는 평평한 `Int64Property` 인데 `Level` 은 중첩된 `ByteProperty` 다.
잘못 쓰면 **인코드 시점에서야** 터진다. 데이터를 이미 망친 뒤다.

그래서 `internal/palsave` 는 트리를 노출하지 않는다. `SetLevel(80)` 만 있고,
범위를 벗어난 값은 잘라내지 않고 거부한다.

**속성이 없는 것과 0은 다르다.** 게임은 기본값이면 필드를 아예 생략한다.
`Level` 이 없는 팰은 1레벨이다. 실제 세이브의 흑천마 54마리가 그 상태였고,
접근자가 1을 반환하고 setter가 속성을 새로 만드는 게 맞다는 걸 확인했다.

## 수직 슬라이스가 잡은 것

CLI를 GUI보다 먼저 만든 이유가 여기서 증명됐다. 단위 테스트로는 못 잡았을
버그 두 개:

**플레이어 UID가 전부 0.** 플레이어 레코드에는 `OwnerPlayerUId` 가 없다.
자기 ID는 `CharacterSaveParameterMap` 의 **맵 키**에 있다. 7명 전원이
"팰 0마리"로 나왔다.

**가득 차 보이는 컨테이너에 아이템 추가 실패.** 슬롯은 희소 구조다. 용량 45에
28칸 점유면 빈 인덱스가 17개 있지만 **배열에는 존재하지 않는다**. 새 요소를
만들어 넣어야 한다.

## 검증 방식

기준점은 같은 편집을 Python으로 먼저 한 결과다. CLI가 그걸 재현하고 값이
일치하는지 본다.

```
팰 99마리 → Lv80 (흑천마 54 / 홍등고래 25 / 제노그리프 20)
석판 354개 → 슬롯 4,  궁극 석판 9개 → 슬롯 17
Money 5,823,423 → 15,823,423,  DogCoin → 700,000
```

슬롯 인덱스까지 동일하게 나왔다. 파일 크기만 2바이트 다른데, 압축 인코더
차이지 데이터 차이가 아니다. **그래서 무결성은 엔티티 개수로 판단한다.**

## 아이콘 — 정책 결정

아이콘 출처로 팬사이트를 긁는 안이 있었으나 접었다. 공개 저장소에 남의
사이트를 긁는 코드가 있으면 그쪽 대역폭에 무단으로 얹는 게 박제되고,
HTML이 바뀌면 깨진다.

다만 **출처를 바꿔도 저작권 문제는 안 없어진다.** 그 이미지는 어디서 가져오든
Pocketpair 것이다. 그래서 진짜 질문은 "저장소에 게임 에셋이 들어가느냐"였고,
답은 **들어가지 않는다**로 정했다.

- 저장소에 있는 것: ID → 파일명 매핑 (게임 자체 명명 규칙, 그냥 데이터)
- 저장소에 없는 것: 이미지 파일 전부
- 사용자가 `scripts/fetch-icons.sh` 로 로컬에 채운다
- 없으면 한글 이름으로 폴백 — 아이콘 없이도 완전히 동작한다

`PalMenuIcon` 이 744/744로 완전 커버라 이쪽을 우선 쓴다. 전신 아트는 레이드
보스 부위 8개가 없다.

**정정 (2026-07-22).** 그 "744/744 완전 커버"가 틀렸다. 업스트림은 809개 항목 중
**567개의 `icon` 필드에 범용 인간 NPC 초상(`t_commonhuman_icon_normal`)을
채워 넣는다.** 빈 값이 아니라 실재하는 파일이라, 커버리지 검사도 `icons.Has()`도
전부 통과하면서 화면에는 후드 실루엣이 그려졌다. 그 중 **169개가 진짜 팰**이고,
세크메트·아누비스·마조리나처럼 팰박스를 채우는 흔한 종들이 여기 포함돼서
"이미지가 많이 깨진다"로 보였다.

교훈은 **"파일이 존재한다"와 "그림이 맞다"는 다른 명제**라는 것. 개수로만 검증하면
둘을 구분하지 못한다 — 무결성을 파일 크기로 판단하지 않기로 한 것과 같은 종류의
실수다.

`PalMenuIcon` 은 이제 진짜 팰이 범용 초상을 달고 있으면 없는 것으로 보고해서
전신 아트로 폴백한다. 인간 NPC는 그대로 둔다 — 그쪽엔 그게 맞는 그림이고
대개 유일한 그림이다.

**그리고 두 번째 버그가 그 뒤에 숨어 있었다.** 남은 5종(`KingWhale_otomo`,
`SheepBall`, `Boss_LazyCatFish`, `Boss_IceFox`, `GhostAnglerFish_Fire`)은 아트가
없는 게 아니라 **조회가 대소문자를 가려서 못 찾은 것**이었다. 세이브와 테이블의
철자가 다르다:

| 세이브 | 테이블 |
|---|---|
| `Boss_IceFox` | `IceFox` (접두사가 `BOSS_` 대문자로만 처리되고 있었다) |
| `SheepBall` | `Sheepball` |
| `LazyCatFish` | `LazyCatfish` |
| `GhostAnglerFish_Fire` | `GhostAnglerfish_Fire` |
| `KingWhale_otomo` | `KingWhale` (`_Otomo` = 동행 형태) |

**테이블의 대소문자는 권위가 없다. 읽어야 하는 쪽은 세이브다.** 그래서 조회를
케이스 폴딩한다 — 전체 키를 소문자로 낮췄을 때 충돌이 0건이라 모호해지지 않는다.
정확 일치는 여전히 최우선이라, 실재하는 `BOSS_*` 키 34개(현상범 인간 NPC)와
`GYM_ElecPanda_Otomo` 는 자기 자신으로 해석된다.

실측: 세이브의 **216종 전부** 한글 이름과 종족별 그림을 받는다. 이건
`TestRealSaveEveryPalIsNamedAndDrawn` 이 고정한다 — 개수만 세면 두 버그 다
놓치므로(첫 번째는 "맞는 개수, 틀린 그림", 두 번째는 216 중 5라 반올림에 묻힌다),
사용자가 실제로 보는 두 가지 — 이름과 종족별 그림 — 를 직접 검사한다.

## 릴리스 — 배포판에 넣으면 안 되는 것

`.github/workflows/release.yml` 이 `v*` 태그를 밀면 윈도우 빌드를 만들어
GitHub Release에 붙인다. Actions 탭에서 수동 실행하면 릴리스는 안 만들고
zip만 올려서 포장만 확인할 수 있다.

**가장 중요한 건 무엇을 빼느냐다.** `build.sh` 는 `assets/icons` 를 exe 옆으로
복사한다(로컬 실행에 필요해서). 그래서 `build/bin` 을 통째로 압축하면 **팰월드
텍스처 2,462장, 34MB가 그대로 배포된다.** THIRD_PARTY.md 가 "저장소는 아트를
절대 배포하지 않는다"고 못 박아둔 바로 그것이다. GitHub Release는 깃에 커밋하는
것보다 더 공개적인 배포지 덜한 게 아니다.

그래서 포장 단계는 `build/bin` 을 복사하지 않고 **파일을 하나씩 나열**한다.
그리고 그것만으로는 나중에 누가 실수할 수 있으니, **zip 직전에 `.webp` 가
하나라도 있으면 빌드를 실패시킨다.** 주석은 잊히지만 실패하는 검사는 안 잊힌다.

결과: 20MB (exe 14MB + CLI 5.6MB + DLL 0.5MB + 문서). 아트 0장.

포장한 그대로 빈 디렉터리에서 실행해 확인했다 — `palsave.exe codec` 통과,
46MB 세이브 파싱 성공. "필요한 파일을 다 넣었나"는 실행해봐야 아는 것이다.

ooz는 벤더링이 아니라 clone이라 CI에서 받아오는데, THIRD_PARTY.md에 적힌
리비전으로 **고정**했다. 안 그러면 상류가 바뀔 때 배포물이 조용히 달라진다.

**GPL-3 의무**: 바이너리를 배포하면 대응 소스를 제공해야 한다. 저장소가 공개고
릴리스에 태그가 붙으니 같은 자리에 소스가 있다 — 릴리스 노트에 그걸 명시한다.

## 팰 추가 — 슬롯 규칙과 그걸 고정한 방법

같은 세이브를 파이썬으로 다루던 시절 **4번 실패하고** 원인을 찾은 적이 있다.
증상은 항상 같았다: **"매번 정확히 1마리만, 항상 같은 슬롯 번호에 생존"**.

한 번 규칙을 찾은 뒤로는 빈 칸에 넣는 것 자체는 문제가 없었다. 위험한 건
발견 과정이었지 동작이 아니다 — 이 절은 그 규칙을 코드로 못 박은 기록이다.

팰박스 슬롯 엔트리에는 **`SlotIndex` 가 `RawData` 바깥에 따로** 있다. 기존
슬롯을 복제해서 `instance_id` 만 바꾸면 `SlotIndex` 가 원본 값 그대로 딸려온다.
그러면 새로 넣은 팰이 전부 같은 슬롯을 주장하고, 게임이 로드하면서 충돌을
정리하며 **마지막 1마리만 남기고 나머지를 지운다. 원래 그 자리에 있던 팰까지
같이 사라진다.**

지켜야 할 것:

1. 슬롯 엔트리의 `SlotIndex` 와 팰의 `SaveParameter.SlotId.SlotIndex` **양쪽 다**
   같은 값으로 쓴다.
2. **배열 위치 ≠ SlotIndex.** 실제 박스가 엔트리 149개인데 `SlotIndex` 는
   0~186이었고 87개가 불일치했다. 배열은 그냥 리스트고 기준은 `SlotIndex` 다.
3. 빈 번호는 **슬롯 엔트리들의 `SlotIndex` 집합**에서 계산한다. 팰 쪽 `SlotId`
   로 계산하면 안 된다 — 박스를 떠난 팰이 stale `SlotId` 를 들고 있어 오염된다.
4. `custom_type`·`CustomVersionData` 같은 부속 필드 때문에 복제는 하되,
   `SlotIndex` 는 반드시 덮어쓴다.
5. 길드 명부 `GroupSaveDataMap[길드].RawData.individual_character_handle_ids` 에
   `{guid: 소유자UID, instance_id: 팰UID}` 를 추가한다(거점 팰은 guid가 0).

팰 자체는 **기존 팰을 복제해서** `CharacterID`/`Gender`/`Level`/`Rank`/
`PassiveSkillList`/`InstanceId`/`SlotId` 만 교체하는 쪽이 안전하다. 단
`EquipWaza`/`MasteredWaza` 는 비운다 — 원본 종의 기술이 딸려온다. 그리고
**Rank 1 팰은 `Rank` 필드가 아예 없어서** 새로 만들어 넣어야 한다.

### 실제로 확인한 것 (2026-07-22)

세이브에서 직접 재확인한 구조:

- 슬롯 엔트리 키는 `[SlotIndex RawData CustomVersionData]` — `SlotIndex` 는
  확실히 `RawData` **바깥**이다.
- **배열 위치 ≠ SlotIndex**: 한 컨테이너는 엔트리 340개인데 그중 **339개가**
  위치와 인덱스가 다르다. 다른 컨테이너는 엔트리 377개에 최대 인덱스가 959다.
- 팰박스 용량은 컨테이너의 `SlotNum` (팰박스 960, 파티 5).
- 이 세이브의 모든 슬롯 엔트리는 이미 차 있다. 즉 추가는 **append** 다.

### 어떻게 고정했나

`FreeSlotIndex` 는 **슬롯 엔트리의 `SlotIndex` 집합**에서만 계산한다. 팰의
`SlotId` 로 계산하지 않는다 — 박스를 떠난 팰이 stale `SlotId` 를 들고 있다.
그리고 `AddPal` 은 그 한 값을 슬롯 엔트리와 팰의 `SlotId` **양쪽에** 쓴다.

핵심 테스트는 개수가 아니라 **집합**을 본다: 추가 전 인스턴스 ID 전부가 추가
후에도 있어야 한다. 개수만 세면 "1마리 잃고 1마리 얻는" 이 버그가 그대로
통과한다.

그리고 **의도적으로 버그를 재현해서 테스트가 잡는지 확인했다.** `appendSlot`
이 항상 `SlotIndex 0` 을 쓰도록 바꿨더니 정확히 옛날 증상이 났다:

```
slot index 0 is claimed twice
after reopen, slot 0 is claimed twice
```

왕복 검증도 했다 — 5마리를 넣고 디스크에 저장한 뒤 **새 App 으로 파일을 다시
열어서** 확인한다. 캐릭터 1,670 → 1,675, 잃은 팰 0, 중복 슬롯 0.

팰 레코드는 기존 팰을 **인코드→디코드로 깊은 복사**해서 만든다. 구조체를 손으로
베끼면 트리를 공유하게 되고, 팰 레코드에는 의미를 모르는 필드가 많아 처음부터
짓는 것보다 동작하는 것을 복사해 아는 부분만 갈아끼우는 쪽이 안전하다.
`EquipWaza`/`MasteredWaza`/`NickName` 은 지운다 — 원본 종의 기술과 이름이
딸려온다.

> 5~7번은 "세이브에 그 데이터가 있는지 확인 전"이라고 적어뒀던 것들이고,
> 셋 다 확인부터 하고 구현했다. 5번은 오프셋 근거를 아래 절에 남겼다.

## 거점 창고 — 상자와 거점을 잇는 두 필드

창고·화로·먹이통처럼 아이템을 담는 시설은 `BaseCampSaveData` 가 아니라
`MapObjectSaveData` 에 있다. 둘 다 프로퍼티 트리에는 불투명한 바이트로만
보이는 블롭 안에 있어서, 오프셋을 직접 찾아야 했다.

- `Model.RawData` **+32** — 이 시설이 속한 거점 GUID. 월드에 널린 보물상자는
  여기가 0이라, 이 필드 하나가 "내 거점 상자"와 "던전 상자"를 가른다.
- `ConcreteModel.ModuleMap["…::ItemContainer"].RawData` **+0** — 아이템
  컨테이너 GUID. `ItemContainerSaveData` 의 키와 같은 값이라 기존 인벤토리
  읽기·쓰기가 그대로 붙는다.

**+32 가 진짜 거점 필드라는 근거**: 이 위치가 0이 아닌 맵 오브젝트가 2,229개인데
**2,229개 전부** 이 세이브가 아는 거점이다. 하나도 빗나가지 않는다. GUID 모양의
엉뚱한 필드를 짚었다면 이 비율이 이렇게 나올 수 없다. 아이콘 때 "해석되는
개수"만 세다가 틀렸던 적이 있어서, 이번엔 맞은 개수가 아니라 **빗나간 개수가
0인지**를 봤다.

전체 7,001개 중 컨테이너를 가진 것이 4,432개, 그중 거점 소속은 147개다.
나머지는 대부분 월드 보물상자(2,597개)라, 거점 필터가 깨지면 UI가 즉시
쓰레기로 덮인다 — 그래서 `TreasureBox` 가 새어들어오면 실패하는 테스트를 뒀다.

예외 하나: `Expedition` 시설 한 개가 `ItemContainerSaveData` 에 없는 컨테이너를
가리킨다. 읽거나 쓸 슬롯이 없으니 창고 목록에서 뺀다.

건물 한글 이름표는 없다. 팰·아이템과 달리 건물 이름 테이블을 아직 안 만들어서,
`ItemChest_04` 같은 게임 내부 이름을 그대로 보여준다. **지어내지 않았다.**

## 실사용 왕복 검증 — 처음으로 확인됨

2번 항목에 "편집 후 저장까지 왕복을 확인해야 한다"고 적어둔 게 오래 남아
있었는데, 거점 창고 경로에 대해서는 확인했다
(`TestCampStorageEditSurvivesSaveAndReopen`).

픽스처를 임시 폴더에 복사해 열고 → 거점 상자에 아이템을 넣고 → `SaveToDisk` 로
디스크에 쓰고 → **새 `App` 인스턴스로 그 파일을 다시 연다.** 내가 방금 쓴
메모리를 되읽는 건 검증이 아니라는 걸 전에 배웠기 때문에, 굳이 프로세스 안의
객체를 버리고 바이트에서 다시 시작한다.

총량이 아니라 **증분**을 본다. 이미 그 아이템이 들어 있는 상자였다면 "최소 N개
이상" 같은 검사는 아무것도 안 한 코드도 통과시킨다. 쓰기를 no-op으로 바꿔
테스트가 실제로 실패하는 것까지 확인했다.

팰 편집 경로는 아직 이 왕복을 안 거쳤다.

## 노동 적성 — 세이브가 저장하는 값의 정체

`GotWorkSuitabilityAddRankList` 는 팰마다 `{WorkSuitability, Rank}` 배열이다.
실제 세이브로 확인한 것:

- **책으로 더한 증분이지 합계가 아니다.** 결정적 근거는 1,730마리 중 76마리만
  이 항목을 가진다는 것 — 합계라면 타고난 적성이 있는 모든 팰이 가져야 한다.
- 종족 기본값과 대조하면 21건 일치 / 78건 초과 / 46건 미달. 기본값도 아니고
  기본+보너스도 아니다.
- 관측값 1~8. 게임 상한은 **10**, 팰 레벨 상한은 **80** (사용자 확인, 코드에 반영).

**미해결 — 증분과 종족 기본값이 게임 화면의 등급으로 어떻게 합쳐지는지 모른다.**
그래서 UI는 "기본 N" 과 보너스를 따로 보여주고 **합계를 주장하지 않는다**.
검증 못 한 값을 숫자로 단정하면 사용자가 그걸 믿고 잘못 편집한다.

게임 안에서 확인되면 `describeWork`(app.go)와 노동 적성 섹션의 안내 문구를
합계 표시로 바꿀 수 있다. 그 전까지는 지금 형태를 유지할 것.
